# Музыкальный мессенджер (TheBoys)

Распределённый музыкальный мессенджер с гарантированной доставкой сообщений, реплицированным хранилищем треков и автоматическим обнаружением отказов.
Подробная архитектура, протоколы и технические сценарии описаны в [Техническом решении](docs/tr.md).

## Структура проекта
- `services/` — исходный код сервисов (FastAPI, шаблоны, статика, тесты)
- `infra/` — конфигурации инфраструктуры (балансировщик Nginx, SQL-схема и миграции PostgreSQL)
- `docs/` — ТР (техрешение), архитектурные схемы и спецификации
- `.github/` — CI/CD workflows, шаблоны задач и PR

## Запуск инфраструктуры

На текущем этапе Docker Compose разворачивает **инфраструктурный фундамент**:
- СУБД **PostgreSQL 16** с версионируемыми миграциями схемы данных;
- Обратный прокси-балансировщик **Nginx 1.27** с блокировкой внутренних API (`/internal/*`) и динамическим обнаружением узлов бэкенда.
  > **Архитектурное примечание:** Nginx динамически распределяет трафик и изолирует отказы узлов приложения, однако сам по себе в данной базовой конфигурации Compose запускается в единственном экземпляре без резервирования (является единой точкой входа / SPOF балансировщика).
- Сервис **узла приложения (`app`)** в режиме валидации протокола и проверки контрактов WebSocket (Contract Verification Stub).
  > **Примечание о границах текущего этапа:** Полнофункциональный веб-интерфейс (UI), узлы распределённого хранения аудиофайлов (`storage`), воркеры фоновых задач (`worker`) и транзакционная бизнес-логика приложения с БД будут подключены на последующих этапах интеграции согласно ТР.

### 1. Настройка окружения и секретов

Для проекта предусмотрено два режима конфигурации секретов:

1. **Локальный режим разработки (Local Development):**
   По умолчанию Docker Compose содержит тестовые плейсхолдеры (`SESSION_SECRET`, `INTERNAL_SECRET`, пароль БД) исключительно для быстрого локального запуска разработчиком «из коробки». **Данные значения по умолчанию являются общеизвестными тестовыми заглушками и категорически не подходят для открытых сетей и общего доступа.**

2. **Боевой/стейджинг режим (Production/Staging):**
   Для любого общего или рабочего окружения обязательно скопируйте файл конфигурации и сгенерируйте уникальные 32-байтные криптографические ключи, чтобы исключить компрометацию сессионных cookie:
   ```bash
   cp .env.example .env
   # Генерация уникальных секретов:
   python -c "import secrets; print('SESSION_SECRET=' + secrets.token_hex(32))"
   python -c "import secrets; print('INTERNAL_SECRET=' + secrets.token_hex(32))"
   ```

### 2. Запуск контейнеров

По умолчанию в `docker-compose.yml` для сервиса `app` задано `scale: 2`. Стандартная команда запуска **автоматически поднимает сразу два взаимозаменяемых узла приложения**:

```bash
# Старт инфраструктуры со сборкой образа (2 узла app по умолчанию):
docker compose up --build

# Фоновый запуск:
docker compose up -d
```

- **Распределение нагрузки:** Каждый узел автоматически получает уникальный `node_id` (на основе hostname контейнера). Nginx динамически балансирует трафик между обоими экземплярами через Docker DNS (`resolver 127.0.0.11 valid=5s`).
- **Отказоустойчивость:** При остановке одного из узлов второй продолжает бесперебойно обслуживать все запросы без ошибок 502/504.
- **Дополнительное масштабирование:** При необходимости число узлов можно изменить:
  ```bash
  docker compose up --scale app=3 -d
  ```

Входная точка через балансировщик Nginx:
- **HTTP API узла приложения:** `http://localhost` (или `http://localhost:8080`, если задан `NGINX_PORT=8080` в `.env`). *Обратите внимание:* пользовательский веб-интерфейс (UI) в данном образе пока не подключён — узел запущен в режиме контрактной заглушки протокола WebSocket и сервисных API;
- **Проверка доступности балансировщика:** `http://localhost/nginx-health`;
- **Проверка доступности узла приложения:** `http://localhost/health`;
- **Прямой доступ к PostgreSQL:** `127.0.0.1:5432` (доступ ограничен `localhost` в целях безопасности).

### 3. Управление миграциями базы данных

Схема базы данных версионируется в каталоге `infra/postgres/migrations/`.

- **Создание с нуля (пустой том):**
  При первом запуске на чистом томе `init.sql` автоматически создает актуальную схему (все таблицы, индексы, CHECK-ограничения) и регистрирует примененные миграции в таблице `schema_migrations`.

- **Обновление существующей базы без потери данных:**
  При изменении структуры схемы выполните миграции одной из команд:
  ```bash
  # Из контейнера PostgreSQL (рекомендуемый способ, строгая атомарность --single-transaction):
  docker compose exec -T postgres sh /docker-entrypoint-initdb.d/migrate.sh

  # Либо через Python-раннер миграций:
  python -m infra.postgres.migrate apply
  ```
  Просмотр статуса миграций:
  ```bash
  python -m infra.postgres.migrate status
  ```

## Тестирование

```bash
# 1. Запуск статических и контрактных тестов:
pytest services/app/tests/ -v

# 2. Запуск инфраструктурных тестов (с проверкой live PostgreSQL и Nginx при поднятом Compose):
# Требуются запущенные сервисы: docker compose up -d
TEST_DATABASE_URL="postgresql://theboys_user:theboys_secret_pass@127.0.0.1:5432/theboys" \
TEST_NGINX_URL="http://127.0.0.1:80" \
pytest services/app/tests/test_infra.py -v
```

## Как работать в репозитории

1. **Создание ветки:** Создайте ветку от `main`:
   ```bash
   git checkout -b feature/<task-name>
   ```
2. **Разработка:**
   - Пишите сервисы в `services/<service>/`.
   - Инфраструктурный код и оркестрацию ведите в `infra/` и `docker-compose.yml`.
   - Утверждённое ТР (`docs/tr.md`) в рамках локальных PR не меняется без предварительного согласования.
3. **Фиксация изменений:** Пишите понятные коммиты на английском языке в формате Conventional Commits (`feat:`, `fix:`, `ci:`, `test:`).
4. **Тестирование:**
   - Запуск тестов: `pytest services/app/tests/ -v`.
   - Перед созданием PR убедитесь, что тесты проходят и проект собирается в Docker.
5. **Создание Pull Request:**
   - Откройте PR в ветку `main`.
   - Заполните шаблон PR (`.github/PULL_REQUEST_TEMPLATE.md`).

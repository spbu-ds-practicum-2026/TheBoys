# Интерфейс узла приложения

Страницы, статика и клиентский код мессенджера. По ТР («Архитектура системы», узел приложения) страницы отдаёт тот же узел FastAPI, что обслуживает API и WebSocket, поэтому интерфейс живёт в `services/app`, а не в отдельном сервисе.

## Состав

| Путь | Назначение |
|---|---|
| `web/pages.py` | Маршруты страниц `/`, `/login`, `/music`, `/chats`; `mount_web(app, get_user)` подключает их и `/static` |
| `templates/` | Jinja2: `shell.html` (оболочка с плеером), `login.html`, фрагменты `music/catalog.html`, `chats/view.html` |
| `static/css/app.css` | Тёмная графитовая тема |
| `static/js/` | ES-модули без сборщика, `htmx.min.js` (2.0.4) |
| `dev/server.py` | **Только для разработки интерфейса**: REST и `/ws` в памяти |
| `tests/` | `test_pages.py`, `test_dev_ws.py` (pytest), `js/store.test.mjs`, `js/session.test.mjs`, `js/ws.test.mjs` (`node --test`) |

Узел приложения подключает интерфейс одной строкой: `mount_web(app, get_user)`, где `get_user(request)` возвращает `{"id", "login"}` по подписанной cookie `session` или `None`.

## Как устроено

- Запрос с заголовком `HX-Request` получает фрагмент раздела, остальные — страницу целиком (`Vary` выставлен). Запрос возврата по истории (`HX-History-Restore-Request`) тоже получает страницу целиком.
- Оболочка (`#app`), мини-плеер и `<audio>` стоят вне `#main` — области, которую заменяет HTMX. Поэтому музыка не прерывается при смене раздела (ТР, сценарий 3), а `Session` и WebSocket живут всё время работы.
- В разметке нет inline-обработчиков: только `data-action` и делегирование событий в `app.js`. Пользовательский текст попадает в DOM только как `textContent` (`dom.js`); тесты запрещают `innerHTML` в скриптах.
- Интерфейс только на русском.

### Клиентский протокол (`static/js`)

| Модуль | Ответственность |
|---|---|
| `store.js` | Чистая логика без DOM: окно истории, `known_seq`, непрочитанные, очередь неподтверждённых |
| `session.js` | Связывает хранилище, WebSocket и REST: сверка, догрузка, повтор после обрыва |
| `ws.js` | `/ws`, переподключение с растущей паузой, регулярный `ping`; нет ответа `dialog_sync` — соединение открывается заново |
| `chat.js`, `catalog.js`, `player.js`, `modal.js` | Виды |
| `app.js`, `login.js` | Точки входа оболочки и страницы входа |

Правила `store.js` — из ТР («Синхронизация истории на клиенте», сценарии 5 и 6):

- `known_seq` растёт из четырёх источников: список диалогов, `dialog_sync`, входящее `message`, `ack` своего сообщения;
- диалог открывается с последних сообщений: `sync` с `before_seq = known_seq + 1`; прокрутка вверх — `sync` с `before_seq` = начало окна;
- окно растёт вниз только следующим по номеру сообщением; сообщение через пропуск не показывается, а `known_seq` обгоняет конец окна и запускает `sync` с `since_seq` = конец окна;
- повторно полученное сообщение узнаётся по `seq`; сообщение или сверка по незнакомому диалогу перезагружает список диалогов, окна не трогает;
- отправка: `client_msg_id` создаётся на клиенте, сообщение «отправляется» до `ack`; после переподключения неподтверждённые уходят повторно с теми же `client_msg_id`, прочитанные позиции — тоже;
- прочитанным сообщается конец окна, счётчик берётся из `read_ack`.

## Запуск и проверка

Из корня репозитория. Зависимости: `pip install -r services/app/requirements-dev.txt` (в `requirements.txt` есть `jinja2`).

```bash
python -m uvicorn services.app.dev.server:app --reload --port 8000
python -m pytest services/app/tests/
node --test services/app/tests/js/*.test.mjs
```

Сайт нужно открывать по адресу из `ALLOWED_ORIGINS` (по умолчанию `http://localhost:8000` или `http://127.0.0.1:8000`): как и настоящий узел, dev-сервер закрывает `/ws` с кодом `4403` для другого `Origin`, и клиент показывает, что подключение отклонено. Для показа с другого устройства запустите сервер с `--host 0.0.0.0` и добавьте адрес, по которому откроют сайт (например, `http://192.168.1.10:8000`), в `ALLOWED_ORIGINS`, иначе `/ws` закроется с кодом `4403`.

Dev-сервер хранит всё в памяти (после перезапуска пользователей нет), проверяет события теми же схемами `services/app/schemas`, что и настоящий узел, и повторяет его правила: `seq = last_seq + 1`, повтор по `client_msg_id` не расходует номер, cookie `{user_id}.{issued_at}.{hmac}` со сроком действия. Чтобы проверить потерю связи: `curl -X POST localhost:8000/dev/drop-connections` — клиенты должны показать «Переподключение…» и доставить неподтверждённые сообщения без дублей.

Рабочий `services/app/main.py` dev-сервер не импортирует и страницы не отдаёт: пока он остаётся заглушкой протокола (нет `/api/*` и БД, на `ping` он не отвечает), интерфейс проверяется только на dev-сервере. Подключить страницы к узлу — `mount_web(app, get_user)` из `web/pages.py` — нужно, когда бэкенд даст вход и API; тогда dev-сервер удаляется.

## REST API, которого ждёт интерфейс

Все ответы JSON, кроме указанных. Ошибка — `{"code": "...", "message": "..."}`. Без входа `/api/*` отвечает `401`.

| Запрос | Успех | Ошибки |
|---|---|---|
| `POST /api/register` `{login, password}` | `201 {user: {id, login}}` + cookie `session` | `409 LOGIN_TAKEN`, `422 INVALID_INPUT` |
| `POST /api/login` `{login, password}` | `200 {user}` + cookie | `401 INVALID_CREDENTIALS` |
| `POST /api/logout` | `204`, cookie удаляется | |
| `GET /api/tracks?q=` | `200 [{id, title, artist, duration_s}]`; поиск по названию и исполнителю без учёта регистра, пустой `q` — весь каталог | |
| `GET /api/tracks/{id}/stream` | `200` / `206` с заголовком `Range`, `audio/mpeg` | `404 TRACK_NOT_FOUND`, `416` |
| `GET /api/users?login=` | `200 [{id, login}]`; совпадение по части логина, без самого пользователя | |
| `GET /api/users/{id}/status` | `200 {online: bool}` | |
| `GET /api/conversations` | `200 [{id, peer: {id, login}, last_seq, unread_count}]` | |
| `POST /api/conversations` `{peer_id}` | `200` тот же объект; диалог существующий или новый | `404 USER_NOT_FOUND` |

WebSocket `/ws` — события и схемы из `services/app/README.md`. Закрытие с кодом `4401` — клиент уходит на `/login`; `4403` (недопустимый `Origin`) — клиент не повторяет подключение и сообщает об отказе.

## Расхождения с ТР и открытые вопросы

- ТР не называет эндпоинт открытия диалога (сказано, что диалог открывается после `GET /api/users?login=…`) и выход из системы. Здесь введены `POST /api/conversations` и `POST /api/logout`; их нужно согласовать с бэкендом и внести в ТР в одном PR с узлом приложения.
- Список диалогов по ТР возвращает только `last_seq` и счётчик, поэтому превью последнего сообщения показывается лишь у диалогов, чьё окно уже загружено.
- В `GET /api/conversations` поля названы `id`, `last_seq`, `unread_count`, а в событии `dialog_sync` — `conversation_id`, `last_seq`, `unread_count`; имена стоит согласовать с бэкендом, пока API не реализован.

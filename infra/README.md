# Инфраструктура проекта (`infra/`)

Модуль оркестрации, балансировки нагрузки, управления схемой и хранилища данных распределенной системы TheBoys.

---

## Архитектурные компоненты

### 1. Балансировщик и обратный прокси Nginx (`infra/nginx/nginx.conf`)
- **Единая входная точка:** Принимает внешние HTTP-запросы и постоянные WebSocket-соединения (`/ws`).
- **Безопасность кластера:** Блокирует внешний доступ к внутренним межсервисным эндпоинтам (`location ^~ /internal/` возвращает `403 Forbidden`). Межузловая доставка (`POST /internal/deliver`) доступна только внутри кластерной сети.
- **Динамический Service Discovery:** Использует встроенный DNS Docker (`resolver 127.0.0.11 valid=5s ipv6=off`) и динамический upstream (`set $app_upstream "app:8000"`). При масштабировании узлов приложения (`docker compose up --scale app=N`) Nginx автоматически обнаруживает новые контейнеры и распределяет запросы между ними без перезагрузки или прерывания существующих соединений.
- **Мониторинг:** Эндпоинт `/nginx-health` для проверки работоспособности самого прокси.

### 2. Схема и миграции PostgreSQL (`infra/postgres/`)

Схема спроектирована в строгом соответствии с ТР:

- `users` — учетные записи пользователей. Уникальность логинов без учёта регистра обеспечена функциональным индексом `CREATE UNIQUE INDEX unique_users_login_lower ON users (LOWER(login))`. Исходный регистр сохраняется для отображения в UI, а поиск `GET /api/users?login=` однозначен.
- `node_registry` — реестр узлов системы (роли `app`, `storage`, `worker`), отметки heartbeat для обнаружения сбоев.
- `conversations` — диалоги. Уникальный индекс `UNIQUE(LEAST(user1_id, user2_id), GREATEST(user1_id, user2_id))` гарантирует существование ровно одного диалога для пары пользователей независимо от порядка. Счётчик `last_seq` снабжён проверкой `CHECK (last_seq >= 0)`.
- `messages` — история сообщений:
  - **Предотвращение дублирования номеров:** Ограничение `UNIQUE(conversation_id, seq)` исключает коллизии номеров внутри диалога. Сама строгая выдача номеров без пропусков обеспечивается транзакционным алгоритмом приложения с блокировкой строки диалога.
  - **Ключ идемпотентности сообщений:** `UNIQUE (conversation_id, sender_id, client_msg_id)`. Разные отправители с одинаковым UUID не конфликтуют. Повторная вставка сообщения от того же отправителя в рамках диалога блокируется СУБД, а на уровне приложения возвращает существующее сообщение без инкремента `seq`.
  - **Базовые ограничения:** `CHECK (seq > 0)`.
- `conversation_reads` — позиции прочтения сообщений участниками (`CHECK (last_read_seq >= 0)`).
- `sessions` — активные WebSocket-подключения клиентов. Внешний ключ `node_id REFERENCES node_registry(node_id) ON DELETE CASCADE` связывает сессию с зарегистрированным узлом (узел сначала регистрируется в реестре, затем принимает подключения).
- `tracks` — каталог аудиофайлов. Ограничения целостности: `CHECK (duration_s > 0)` и `CHECK (size_bytes >= 0)`. Поиск оптимизирован индексами `LOWER(title)` и `LOWER(artist)`.
- `replicas` — размещение двух реплик каждого трека на узлах хранения.
- `jobs` — очередь фоновых задач (репликация) с поддержкой распределенной аренды (lease) и токенов ограждения (fencing tokens):
  - `CHECK (fencing_token >= 0)`;
  - Для задач репликации обязателен трек: `CHECK (task_type != 'replicate' OR track_id IS NOT NULL)`;
  - Для активных задач в статусе `running` обязательны непустой `worker_id` и заданный `lease_until`: `CHECK (status != 'running' OR (worker_id IS NOT NULL AND length(trim(worker_id)) > 0 AND lease_until IS NOT NULL))`.

#### Проверки, возлагаемые на серверную бизнес-логику
Ряд проверок по ТР не могут быть выражены простыми ограничениями СУБД и реализуются в серверной транзакции приложения:
1. **Участие пользователя в диалоге:** Проверка, что `sender_id` сообщения является либо `user1_id`, либо `user2_id` данного диалога.
2. **Монотонность позиции прочтения и её границы:** Проверка `new_read_seq >= old_read_seq` и `new_read_seq <= last_seq` (нельзя прочитать сообщения, которые ещё не существуют).
3. **Валидация содержимого сообщений:** Проверка структуры `payload` в зависимости от `kind` (для `track` — проверка существования `track_id` в каталоге `tracks`).
4. **Транзакционная выдача последовательных `seq`:** Выполняется под блокировкой `SELECT last_seq FROM conversations WHERE id = :cid FOR UPDATE` с предварительной проверкой существующего `(conversation_id, sender_id, client_msg_id)`.
5. **Проверка актуального токена воркера:** Сверка переданного `fencing_token` с текущим токеном задачи в БД перед фиксацией результатов фоновой работы.

## Версионирование миграций

Каталог `infra/postgres/migrations/` содержит SQL-файлы миграций:
- `0001_initial_schema.sql` — базовый снимок начальной схемы;
- `0002_constraints_and_idempotency.sql` — обновление схемы: составной ключ идемпотентности `(conversation_id, sender_id, client_msg_id)`, регистронезависимый индекс логинов, CHECK-ограничения и FK сессий.

История применения миграций фиксируется в таблице `schema_migrations`.

### Применение миграций:
- **С нуля:** `infra/postgres/init.sql` автоматически создает схему и проставляет отметки о примененных миграциях.
- **Обновление работающей базы данных:**
  ```bash
  # Из контейнера Postgres:
  docker compose exec -T postgres sh /docker-entrypoint-initdb.d/migrate.sh

  # Либо через утилиту migrate.py:
  python -m infra.postgres.migrate apply
  ```

## Безопасность и настройка секретов

- **Доступ к PostgreSQL:** В `docker-compose.yml` порт PostgreSQL опубликован строго на локальном интерфейсе (`127.0.0.1:5432:5432`), что исключает доступ к СУБД из внешней сети хоста. Контейнеры кластера обращаются к базе по внутреннему имени `postgres:5432`.
- **Секреты (`SESSION_SECRET`, `INTERNAL_SECRET`):**
  - В локальном режиме разработки (dev) используются значения по умолчанию для быстрого запуска.
  - В production/staging обязательна генерация уникальных случайных ключей в файле `.env` (`python -c "import secrets; print(secrets.token_hex(32))"`). Утечка `SESSION_SECRET` недопустима, так как ключ используется для криптографической подписи session cookie пользователей.

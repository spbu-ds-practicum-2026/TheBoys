# Техническое решение проекта «Музыкальный мессенджер»

## Введение

- **Цель проекта:**  
  Реализовать прототип распределённой системы, в которой пользователи слушают треки, переписываются и отправляют треки друг другу в чат. Система работает на нескольких узлах, хранит каждый аудиофайл в двух копиях и продолжает работать при отказе отдельных узлов.

- **Задачи:**
  1. Реализовать мессенджер с обменом треками, работающий на нескольких узлах приложения.
  2. Обеспечить доставку сообщений между узлами без потерь, дублей и с одинаковым порядком у всех участников.
  3. Реализовать собственное реплицированное хранилище аудиофайлов и собственную очередь задач, которые переживают отказ отдельных узлов.
  4. Закрепить на практике решения проблем распределённых систем: ненадёжной доставки, частичных отказов, распределения данных, согласованности и порядка событий.

- **Основания для разработки:**  
  Учебный групповой проект по курсу «Основы распределённых вычислений», СПбГУ, 2026 г.

## Глоссарий
| Термин | Определение |
|---|---|
| Пользователь | Зарегистрированный клиент системы |
| Трек | Аудиофайл в формате MP3 с названием, исполнителем и длительностью |
| Диалог | Переписка двух пользователей |
| Карточка трека | Сообщение в диалоге, из которого собеседник запускает трек |
| Узел | Отдельный процесс системы (контейнер Docker), который работает и отказывает независимо от других |
| Узел приложения | Копия веб-приложения: обслуживает запросы и WebSocket-подключения пользователей, постоянного состояния не хранит |
| Узел хранения | Сервис, который хранит аудиофайлы на собственном диске |
| Воркер | Процесс, выполняющий фоновые задачи из очереди |
| Реестр узлов | Таблица в БД, где узлы регистрируются и регулярно отправляют heartbeat — отметку «я жив» |
| Реплика | Копия аудиофайла на одном из узлов хранения. Каждый трек хранится в двух репликах |
| seq | Порядковый номер сообщения в диалоге; номера идут без пропусков |
| Идемпотентность | Свойство операции: повторное выполнение даёт тот же результат, что и однократное |
| Аренда (lease) | Временное право воркера на задачу. Когда аренда истекает, задачу может забрать другой воркер |
| Токен ограждения | Номер попытки выполнения задачи. Результат воркера с устаревшим токеном отклоняется |

## Функциональные требования
Система должна предоставлять следующие функции:
1. Регистрация и вход по логину и паролю.
2. Каталог треков и поиск по названию и исполнителю.
3. Загрузка своего трека. Название, исполнитель и длительность извлекаются из тегов в фоновой задаче.
4. Прослушивание с перемоткой. Мини-плеер не прерывает музыку при переходе между разделами.
5. Личные сообщения с любым пользователем, история диалога.
6. Отправка трека в чат карточкой, которую собеседник запускает прямо из диалога.
7. Онлайн-статус собеседника, индикатор «печатает…», счётчик непрочитанных.
8. Работа на нескольких узлах приложения: любой запрос обрабатывает любой живой узел, новые узлы обнаруживаются автоматически.
9. Хранение каждого трека в двух копиях на разных узлах хранения и автоматическое восстановление копии после отказа узла.
10. Фоновая обработка через собственную очередь задач с перевыдачей задачи при отказе воркера.
11. Служебная страница `/admin/nodes` с состоянием узлов, копий треков и очереди задач.

### Ограничения на предметную область
1. Принимаются только MP3-файлы размером до 30 МБ.
2. Каталог заполняется треками со свободными лицензиями; авторские права на загружаемые треки система не проверяет.
3. Все узлы работают на одной машине под управлением Docker Compose.

## Нефункциональные требования
1. **Доступность:** при отказе одного узла приложения, одного узла хранения или одного воркера система остаётся доступной; пользователь теряет связь не дольше чем на 10 с.
2. **Надёжность:** отказ узла обнаруживается не позже чем через 15 с. Подтверждённое сообщение не теряется, задача не теряется при отказе воркера, две копии каждого трека восстанавливаются не позже чем через 2 минуты после отказа узла хранения.
3. **Производительность:** на стенде при 100 одновременных пользователях ответ на запросы API — не дольше 200 мс, доставка сообщения на другой узел — не дольше 1 с.
4. **Согласованность:** повторная отправка сообщения не создаёт дубль, порядок сообщений в диалоге одинаков у всех участников.
5. **Масштабируемость:** число узлов приложения (от 2 до 5) задаётся при запуске без изменения кода и конфигурации.
6. **Безопасность:** пароли хранятся в виде хеша, служебные адреса для связи между узлами закрыты снаружи.
7. **Развёртывание:** вся система запускается командой `docker compose up`.
8. **Ограничения технологий:** не используются готовые распределённые решения (брокеры сообщений, распределённые очереди, БД и хранилища, оркестраторы). PostgreSQL работает в одном экземпляре, без репликации.

## Пользовательские сценарии

### Сценарий: послушать трек
1. Пользователь входит и в разделе «Музыка» ищет трек по названию.
2. Нажимает «▶» — трек играет в мини-плеере внизу экрана.
3. Переходит в «Чаты» — музыка не прерывается.

### Сценарий: загрузить свой трек
1. Пользователь нажимает «Загрузить трек» и выбирает MP3-файл.
2. Трек появляется со статусом «обрабатывается», через несколько секунд — «готов», с названием и исполнителем из тегов.
3. Если файл не MP3 или больше 30 МБ, пользователь видит ошибку, и трек не создаётся.

### Сценарий: поделиться треком
1. Алиса нажимает «Отправить в чат» у трека и выбирает Боба.
2. У Боба растёт счётчик непрочитанных, в диалоге появляется карточка трека.
3. Боб нажимает «▶» на карточке, и трек играет у него.

### Сценарий: сбой сервера во время переписки
1. Сервер, к которому подключён Боб, падает.
2. Боб видит «Переподключение…», через несколько секунд чат снова работает.
3. Сообщения, отправленные за это время, появляются в диалоге без потерь и дублей.

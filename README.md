# Музыкальный мессенджер (TheBoys)

Распределённый музыкальный мессенджер с гарантированной доставкой сообщений, реплицированным хранилищем треков и автоматическим обнаружением отказов.
Подробная архитектура, протоколы и технические сценарии описаны в [Техническом решении](docs/tr.md).

## Структура проекта
- `services/` — исходный код сервисов (FastAPI, шаблоны, статика, тесты)
- `infra/` — конфигурации инфраструктуры (балансировщик Nginx, SQL-схема и миграции PostgreSQL)
- `docs/` — ТР (техрешение), архитектурные схемы и спецификации
- `.github/` — CI/CD workflows, шаблоны задач и PR

---

## Запуск инфраструктуры

На текущем этапе Docker Compose разворачивает **инфраструктурный фундамент**:
- СУБД **PostgreSQL 16** с версионируемыми миграциями схемы данных;
- Отказоустойчивый обратный прокси-балансировщик **Nginx 1.27** с блокировкой внутренних API (`/internal/*`) и динамическим обнаружением узлов;
- Сервис **узла приложения (`app`)** в режиме валидации протокола и проверки контрактов WebSocket (Contract Verification Stub).

> **Примечание о границах текущего этапа:** Узлы распределённого хранения аудиофайлов (`storage`), воркеры фоновых задач (`worker`) и транзакционная бизнес-логика приложения с БД будут подключены на последующих этапах интеграции согласно ТР.

### 1. Настройка окружения и секретов

Для проекта предусмотрено два режима конфигурации секретов:

1. **Локальный режим разработки (Local Development):**
   По умолчанию Docker Compose содержит безопасные для локальной отладки значения по умолчанию (`SESSION_SECRET`, `INTERNAL_SECRET`, пароль БД). Проект запускается «из коробки» без обязательного создания `.env`.

2. **Боевой/стейджинг режим (Production/Staging):**
   Обязательно скопируйте файл конфигурации и сгенерируйте уникальные 32-байтные криптографические ключи, чтобы исключить подделку сессионных cookie:
   ```bash
   cp .env.example .env
   # Генерация уникальных секретов:
   python -c "import secrets; print('SESSION_SECRET=' + secrets.token_hex(32))"
   python -c "import secrets; print('INTERNAL_SECRET=' + secrets.token_hex(32))"
   ```

### 2. Запуск контейнеров

```bash
# Старт инфраструктуры со сборкой образа приложения:
docker compose up --build

# Старт с двумя взаимозаменяемыми узлами приложения (горизонтальное масштабирование):
docker compose up --scale app=2 -d
```

Приложение доступно через балансировщик Nginx:
- Веб-интерфейс и HTTP API: `http://localhost` (или `http://localhost:8080`, если указан `NGINX_PORT=8080` в `.env`);
- Проверка доступности балансировщика: `http://localhost/nginx-health`;
- Проверка доступности узла приложения: `http://localhost/health`;
- Прямой доступ к PostgreSQL для локальной отладки: `127.0.0.1:5432` (доступ ограничен `localhost` в целях безопасности).

### 3. Управление миграциями базы данных

Схема базы данных версионируется в каталоге `infra/postgres/migrations/`.

- **Создание с нуля (пустой том):**
  При первом запуске на чистом томе `init.sql` автоматически создает все таблицы, индексы, CHECK-ограничения и регистрирует примененные миграции в таблице `schema_migrations`.

- **Обновление существующей базы без потери данных:**
  При изменении структуры схемы выполните миграции одной из команд:
  ```bash
  # Через скрипт в работающем контейнере PostgreSQL:
  docker compose exec -T postgres sh /docker-entrypoint-initdb.d/migrate.sh

  # Либо через Python-раннер миграций:
  python -m infra.postgres.migrate apply
  ```
  Просмотр статуса миграций:
  ```bash
  python -m infra.postgres.migrate status
  ```

## Как работать в репозитории

1. **Создание ветки:** Создайте ветку от `main`:
   ```bash
   git checkout -b feature/<task-name>
   ```
2. **Разработка:**
   - Пишите сервисы в `services/<service>/`.
   - Инфраструктурный код и оркестрацию ведите в `infra/` и `docker-compose.yml`.
   - Утверждённое ТР (`docs/tr.md`) в рамках локальных PR не меняется без предварительного согласования.
3. **Фиксация изменений:** Пишите понятные коммиты на английском языке в формате Conventional Commits (`feat:`, `fix:`, `ci:`, `test:`).
4. **Тестирование:**
   - Запуск тестов: `pytest services/app/tests/ -v`.
   - Перед созданием PR убедитесь, что тесты проходят и проект собирается в Docker.
5. **Создание Pull Request:**
   - Откройте PR в ветку `main`.
   - Заполните шаблон PR (`.github/PULL_REQUEST_TEMPLATE.md`).
